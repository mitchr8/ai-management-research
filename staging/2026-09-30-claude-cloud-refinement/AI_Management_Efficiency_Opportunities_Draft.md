## 1. Method and evidence base

**What was read.** All 44 mirrored files were available; the 29 files listed above as fully consumed were read end-to-end, and the five large mailboxes/handoffs marked "selective" were read by stable ID, heading, and line range as the workstream instructed. No project-level document (ULTUSB, GO10, Agent Relay, LifeAutomation, Frontier) was read; every statement about those projects is quoted from Management-owned surfaces and is therefore second-hand Management evidence, not project truth. Drive was not called; the manifest's Drive IDs and sha256 values are the provenance of record.

**How quantities were measured.** Character and paragraph counts come from `_manifest.json` fields `clean_chars` / `clean_paragraphs`, which were computed on the plain-text export of each Google Doc. Caveats: (a) Google Drive's own `fileSize` for native Docs is smaller than the exported text (for example the Chief handoff shows 29,754 bytes in Drive metadata but 71,454 exported characters), so Drive-side size is not a usable proxy for the Reliability Contract thresholds; (b) the ratified thresholds are expressed in "characters" and "paragraphs" without specifying the measurement surface, so the Chief's own readback figures (for example "~51,968 document characters / 578 paragraphs" for the pre-Checklist-5 archive [Source: AI_Management_Chief_of_Staff_Handoff_Current.txt § "CHECKLIST #5 — OWNER CONTEXT-PRESERVATION GUARD"]) may differ from the manifest figures for the same file by a few percent; (c) token estimates use chars/4, a crude English-prose heuristic that undercounts for ID-dense text such as `ULTUSB-DA-NOIDLE-BUILDERUX-001`. All token figures are order-of-magnitude only.

**How counts of duplication were produced.** Keyword occurrences were counted per file with case-insensitive `grep -c` on the mirrored text (one count per matching line). These counts therefore undercount where a line contains the term twice and overcount where a term appears in a quotation of a rule rather than a restatement. They are indicators, not audits. The exact patterns used for the ritual-restatement counts in §3.4 and EFF-019 (case-insensitive extended regex, one count per matching line, over all 44 mirrored files) are: `one[- ]task[- ]at[- ]a[- ]time|one Owner-facing task` (49 lines / 19 files; 48 / 19 with the hyphenated form only); `PMs? (retain|remain)` (14 / 9); `Delivery Assurance owns` (16 / 11); `COS-CEO-N-023 remains HOLD` (25 / 11); `Relay remains P0` (17 / 11); `front door|Chief of Staff is the (primary|preferred)` (32 lines). An earlier pass of this draft reported higher figures (62 / 25 / 20 / 26 / 18) from unrecorded patterns; the values above are the reproducible ones and none of the conclusions depends on the difference. Mailbox status counts in §4.4 are `grep -c "^Status:"` line counts over each mirrored file, so they include status lines inside amendment and sub-blocks; a per-stable-ID state was not derived.

**How the 2026-09-30 chain was reconstructed.** The hop list in §2 is built from the Chief handoff's dated event blocks (lines 1003-1410 of the mirror, ~34.8k characters by `wc -c` and ~200 non-blank lines; 26 blocks stamped `Date: 2026-09-30`), cross-checked against the two Executive Operations mailboxes, the Chief mailboxes, the CEO handoff, and the packet files. ## 5. REPEATED MANUAL DELIVERY STEPS — the passive-chat model

### 5.1 Characterisation of the path

For a Management-originated execution packet the designed path is: Owner (intent) -> Chief (Drive write) -> **Owner paste** -> CEO (Drive write) -> **Owner report** -> Chief (reads, renders) -> **Owner paste** -> Delivery (Drive writes) -> **Owner report** -> Chief (reads, renders) -> **Owner paste** -> worker -> **Owner report** -> Chief (reads, DONE). Minimum **3 Owner pastes + 3 Owner report-backs** before the worker's result is reconciled; **4 + 4** when a project PM must disposition first (Chain C). Each paste is preceded by a Chief render and each report is followed by a Chief re-read of durable evidence, so every hop costs two Chief turns (two handoff writes) in addition to the recipient's writes.

This is the architecture the sources describe, not a deviation: "whenever a separate chat must consume a Drive message, AI Management must tell the Owner that manual activation is required" [Source: AI_Management_Current_Structure.md § "Passive inbox execution model — 2026-09-26"]; "no standing CEO automation is active; Drive writes are routing state, not evidence of target-chat execution" [same]; "No standing CEO automation is required for this function. If automation is explicitly authorized later, it is only an Owner-notification surface and never evidence that the separate target chat executed the work" [Source: AI_Management_Brain.md § "Passive inbox and manual activation rule"].

### 5.2 The process correction and what it implies for a "fast path"

The Owner-prompted process correction (a Chief disposition with Owner-approved execution "subject to proper chain review", §2.1) requires CEO and Delivery vetting "Because the prompt would alter behavior of an already-running Relay/Claude lane, it must be treated as an execution packet" [Source: Chief handoff § "PROCESS CORRECTION — TACTICAL CLAUDE RECOVERY PROMPT"]. Two things in the same evidence base cut the other way and must be preserved alongside it:

- the Chief's later ruling that an in-scope follow-up write needs "No new CEO/Delivery approval" [Chief handoff L1077];
- PRODUCT003, a correction packet to the same running Claude lane, was vetted by the ULTUSB PM and Delivery only — the CEO was not in the loop [Source: AI_Management_Executive_Operations_To_CEO_Current.md § "Response-To: ULTUSB-DA-PRODUCT003-CORRECT-001"; Chief handoff L1291-1313].

So the ecosystem already operates two implicit fast paths without having named their criteria. Naming them is design work (EFF-009). Because the full chain is an Owner-prompted Chief process correction with Owner-approved execution "subject to proper chain review" [Chief handoff L979-1005], this document treats loosening it as an Owner decision — the Owner raised the concern — while noting the rule text itself is the Chief's disposition.

### 5.3 Duplicate-suppression machinery that exists because the Owner is the bus

The following mechanisms exist primarily to stop a message being carried twice or a finished lane being re-prompted, in a system where no chat can observe another chat's receipt in real time: SENT_EVENT / DONE_EVENT same-turn binding; `NEEDS_OWNER_PING` / `READY_FOR_CHIEF_RENDERING` counters; "Duplicate check: exactly one canonical packet file exists"; the four-step evidence-first order; the Pending handoff persistence rule; INV-RENDER, INV-SENT, INV-DONE, INV-DELIVERY; "Never recreate a delivered GO10 recovery activation or any other superseded packet from stale state" [AI_Management_Executive_Operations_Delivery_Assurance_Launch_Prompt.md L161]; "Do not create another correction" [AI_Management_Handoff_Current.txt § "IMMEDIATE ULTUSB CLEANUP", L89] [Sources for the rest: AI_Global_Brain.md § "SENT_EVENT / DONE_EVENT"; AI_Management_Executive_Operations_Delivery_Assurance_Launch_Prompt.md § "DUPLICATE SUPPRESSION", § "BOUNDED LIVE INVARIANT CHECKS"; AI_Management_Brain.md § "Pending handoff persistence rule — ratified 2026-09-26"].
